    The core point

    The model is one component, not the product. An AI engineer builds the software around a call that can return something different every time: what goes in (context and tools), what is allowed out (schemas and validation), what it can touch (permissions), and how you know it works (evals and traces). None of it requires training a model.

    1. Weeks 1–3 · Call, validate, measureHow do I get reliable output from an unreliable call?

      API calls, typed output with validation and retries, then evals in CI.

    2. Weeks 4–6 · Tools, retrieval, agentsHow does the model act on real data?

      Tool use and workflow patterns, hybrid retrieval, then an agent loop built by hand and with an SDK.

    3. Weeks 7–9 · ProductionHow do I run it safely and cheaply?

      MCP servers and integrations, tracing and cost, then prompt-injection defenses.

    4. Weeks 10–12 · Deploy and deliverHow do I ship it to a customer and show the work?

      Deployment with eval-gated CI, a forward-deployed customer exercise, then portfolio and interview practice.

    The ladder for this plan is single call → workflow → agent. Only add autonomy when your evals show the simpler version fails. Every week adds to one project, a support-desk assistant for a small online store, so by Week 12 it is a single system you can demo end to end.

    Self-check answers

    Try each one yourself before opening it.

    W1: A response comes back with stop_reason "max_tokens". What happened, and how do you fix it?

    The model hit the output limit you set and the reply is cut off, so any JSON in it is probably broken. Raise max_tokens, ask for a shorter output, or split the task. Always check the stop reason in code instead of assuming the reply is complete.

    W2: The JSON matches the schema, but the order_id doesn't exist. Whose job is it to catch that?

    Yours, in code. Structured output guarantees shape, not truth. A validation layer after the call checks business rules against real data (look the order up), and on failure either re-asks the model with the error or routes the ticket to a human.

    W3: Your LLM judge passes 95% of summaries, but you disagree with it on a third of the ones you checked. What now?

    The judge isn't measuring what you care about yet. Label a set by hand, compare the judge's verdicts with yours, and tighten its prompt with clear pass/fail criteria and examples until agreement is high. Until then, don't trust its numbers.

    W4: When should you build a fixed workflow instead of an agent?

    When the steps are known in advance. A workflow is cheaper, faster, easier to test and easier to debug. Use an agent only when the path really depends on what the model finds along the way, and your evals show the workflow can't handle it.

    W5: Answers are wrong. How do you tell whether retrieval or generation is at fault?

    Measure them separately. For each eval question, check whether the right chunk was in the retrieved top-k (recall@k). If it wasn't, fix retrieval: chunking, hybrid search, reranking. If it was there and the answer is still wrong, fix the prompt or model, and check faithfulness to the retrieved text.

    W6: Your agent sometimes loops calling the same tool forever. Name three causes.

    The tool returns an error or empty result the model doesn't understand, so it retries (return clear, actionable error messages). There's no clear "done" condition (add a finish or escalate tool and say when to use it). There's no hard limit (cap steps and tokens in code). Traces show which one it is.

    W7: Why put tools behind an MCP server instead of defining them in the agent's code?

    Write the integration once and any MCP client can use it: your agent, Claude Desktop, Claude Code, a customer's own tools. It also separates concerns: the server owns auth, permissions and the system's API, and the agent only sees the tools it is given.

    W8: The monthly bill doubled but traffic didn't. Where do you look first?

    Traces, grouped by cost per request. Common causes: an agent taking more steps or retrying, a prompt or tool result that grew (more input tokens on every call), a prompt-cache hit rate that dropped after a prompt change, or traffic routed to a larger model.

    W9: Why isn't "don't issue refunds over $100" in the system prompt a security control?

    The prompt is just more text the model weighs, and injected text can override it. A control has to sit where the model can't change it: the refund tool rejects amounts over the limit, it only sees this customer's orders, and large actions need human approval.

    W10: Why should a prompt change go through the same review and CI as a code change?

    A prompt change changes behavior just as much as code does, often in ways you can't see by reading it. Versioning prompts and running the eval suite on every change catches regressions before they reach users, and makes rollback possible.

    W11: A customer says the bot "feels dumb." What do you do first?

    Get specifics before changing anything. Ask for real examples, pull the traces for them, and find the pattern: wrong facts (retrieval), ignored instructions (prompt), missing actions (tools), or a mismatch with what users actually need. Turn the examples into eval cases, fix the biggest category, and show the before and after.

    W12: "Walk me through what happens between the user pressing enter and the answer coming back."

    For your capstone: the request hits the API, a job is queued, the worker classifies the ticket, the agent calls tools over MCP and retrieves policy chunks, the draft is validated and checked by guardrails, then returned or escalated, with every step traced. Name a failure point and its fix at each step.
